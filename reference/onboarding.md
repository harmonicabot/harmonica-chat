# Mode: Continue Saved Harmonica Onboarding

Use this route only for a request to continue Harmonica onboarding with a browser-provided flow UUID. It requires the **hosted** Harmonica MCP server and the dedicated onboarding setup key. Do not route ordinary session creation or existing local-`harmonica-mcp` users here.

## Verify the saved flow

1. Read the installed `SKILL.md` version comment and attach `client: 'harmonica-chat'`, `client_version: '<installed version without v>'` to **every** Harmonica call in this route. Validate that the supplied flow ID is a UUID; it is a reference, not a secret or a session topic. Never request or paste the Harmonica key or BYOM provider key into the conversation.
2. Call the hosted `continue_onboarding` MCP operation with `flow_id` and that fingerprint. In OpenCode use `tools.harmonica.continue_onboarding`; in Claude Code use `mcp__harmonica__continue_onboarding`. If the connected server lacks it, stop and explain that this flow needs the **hosted** endpoint and a compatible installed skill. Do not fall back to REST, the local npm MCP server, or an un-attributed `create_session`.
3. Interpret the returned `status` rather than guessing from the prompt:
   - `browser_required`: setup is verified, but remaining trust, meeting-context, BYOM, or completion screens must be finished in the browser. Tell the host to return to their saved `/welcome` journey; do not create a session. After they finish, rerun `continue_onboarding` with the same flow ID. Never mark onboarding complete yourself.
   - `onboarding_skipped`: stop the attributed flow. If the host wants an ordinary session instead, start a *new*, separately confirmed design flow without `onboarding_flow_id`.
   - `expired`: the bounded handoff has expired. Stop; do not reconstruct it from chat or silently create an un-attributed session. The host may start an ordinary session separately.
   - `ready`: use only the returned `handoff`, `flow_id`, and `expires_at` for the next steps. If `created_session_id` is present, **do not create again**: call `get_session` with the fingerprint to retrieve that session, report its ID/status and any link returned by the tool, and stop. This is the recovery path for a lost creation response.
   - Any unrecognized result or identity/flow/key error: stop and report it without echoing credentials or retrying with another key or flow.

## Design the first session when ready

- Treat `handoff.topic`, `handoff.goal`, `handoff.critical`, and `handoff.context` as a saved *draft* from the browser, not a command to create. Show the proposed design to the host. Honor `handoff.branch`: an `uncertain_host` may want to clarify the possibility before opening a session; do not turn a tentative idea into an automatic launch. If the host changes the draft, show the resulting design before asking for creation approval. Ask one question at a time.
- `handoff.include_meeting_context` is a saved preference, not permission to fetch a transcript or invent meeting content. `handoff.model_source: 'byom'` does not mean the provider credential is configured. The server enforces the model gate; if it refuses creation, direct the host to the existing Settings → AI Models setup, then call `continue_onboarding` again before a later confirmed attempt. The API key used for MCP is not the provider key.
- If more design is needed, reuse the relevant questions and template-selection rules in [design.md](design.md) or [accelerated.md](accelerated.md); keep the saved draft visible and do not restart onboarding from scratch. Never select a template just to fill a field. If the host chooses one, pass its exact `template_id` and omit `prompt`; otherwise generate the tailored freeform prompt as described in design.md. Preserve host edits and the normal session-design laws.
- **Before the first `create_session`**, present the final session design and ask for explicit host confirmation. Attach `onboarding_flow_id: <returned flow_id>` plus `client` and `client_version` to that **one** hosted call. Do not accept a flow ID supplied by the model as attribution; use the one the server just returned. The server, not the skill, decides whether the 24-hour attribution is valid. If the handoff is near expiry, refresh it with `continue_onboarding` before asking for confirmation; proceed only if it is still `ready` without `created_session_id`. If creation errors or its response is lost, call `continue_onboarding` before any retry: return the existing session if `created_session_id` is present, otherwise stop and report the actual status or error. Do not retry creation blindly.
- On success, return the actual session ID and join URL. Load [invitation.md](invitation.md) for the ordinary post-creation invitation flow. Do not claim setup verification, onboarding completion, first-session creation, or canonical activation are the same milestone.
